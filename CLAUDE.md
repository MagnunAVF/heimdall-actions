# Heimdall Actions: Kubernetes-native CI/CD orchestration engine (Go, React)

## Current focus

Milestone M0 (project setup) is in progress; next is M1 (infrastructure core and authentication).
Roadmap: docs/plans/ROADMAP.md. Milestone plans: docs/milestones/M<k>.md (created by
/plan-milestone). Local stack: Docker Compose for single components, `kind` for the cluster.

## Commands

Nothing is scaffolded yet. The Makefile and these targets arrive with the first code in M1;
keep this list in sync when they change.

- Everything CI runs: `make check` (lint, generated-code diff, tests). Must pass before saying a
  task is done. Never needs a running cluster or external services.
- One Go package's tests: `go test ./internal/<pkg> -run TestName -v`
- Integration tests (need `make up`): `make test-integration`
- After editing SQL in internal/store/queries or migrations: `make generate`
- Local dependencies (Postgres, Redis, RabbitMQ, ClickHouse, Keycloak): `make up` / `make down`
- Local cluster: `make kind-up` / `make kind-down` (cluster name `heimdall`, context `kind-heimdall`)
- Frontend (inside web/): `npm run dev`, `npm test`, `npm run lint`, `npm run typecheck`
- Script and hook tests (until `make check` runs them): `bash scripts/<name>_test.sh`,
  `bash .claude/hooks/hooks_test.sh`

## Architecture (planned; update when a package lands)

- cmd/api → Fiber API entrypoint: config, flags and wiring only.
- cmd/worker → worker entrypoint: config, flags and wiring only.
- internal/api → Fiber handlers, routes, Keycloak JWT middleware, payload validation. No SQL.
- internal/store → the ONLY package that touches PostgreSQL: pgx pool, goose migrations,
  sqlc queries, transactions. internal/store/db is generated by sqlc. Never edit it.
- internal/cache → Redis client and cache-aside helpers (image whitelist, project permissions).
- internal/queue → RabbitMQ publisher (API) and consumer with manual acks (worker).
- internal/k8s → client-go: build batch/v1 Jobs, watch status, tail pod logs. Worker only.
- internal/logs → ClickHouse batch writer and log reader for SSE.
- internal/platform → shared pieces: errs (sentinel errors), config, observability setup.
- web/ → React + TypeScript frontend (Vite), its own npm project. Talks only to the API.
- infra/local → docker-compose.yml (+ .env.example) and the kind config for local development.
- infra/stage, infra/prod → Kubernetes manifests / Helm values per environment (empty for now).

The API never talks to Kubernetes; the worker never serves HTTP to users. They share state only
through PostgreSQL (via the API) and RabbitMQ.

## Conventions

### Go

- Errors: wrap with fmt.Errorf("doing x: %w", err); sentinel errors in internal/platform/errs.
- context.Context is the first parameter of every function that does I/O.
- Dependencies come in through constructors and interfaces. No globals, no init().
- Tests: table-driven, testify require/assert. Unit tests never hit real Postgres, Redis,
  RabbitMQ, ClickHouse, Keycloak or a cluster (use fakes / client-go fake clientset); real calls
  only in files with `//go:build integration`.
- Logging: log/slog, structured, with the execution id on every line about an execution.
- Every queue message and every Kubernetes Job carries the execution UUID.

### TypeScript (web/)

- Strict TypeScript; no `any`. ESLint and Prettier must be clean.
- Server state through a data-fetching layer, not ad-hoc fetch in components.
- Tests: Vitest + React Testing Library. No real network in unit tests (mock the API).

## Security rules

- Every API route except health checks sits behind the JWT middleware. Validate issuer,
  audience, expiry and signature against Keycloak's JWKS.
- A job may only run an image from the whitelist. Validate on the API before publishing; the
  worker re-checks before creating the Job.
- User shell scripts are untrusted: never interpolate them into a host shell, never log
  secrets, and run Jobs with a restricted security context (non-root, no privilege escalation,
  resource limits, activeDeadlineSeconds).
- All SQL goes through sqlc with parameters. Never build SQL with fmt.Sprintf or concatenation.
- Secrets come from env / Kubernetes Secrets. Never commit them, never read .env files.

## Issues, branches and pull requests

- Issues are referenced ONLY as ENG-<n>, the id at the start of the GitHub issue title
  ("ENG-3: [1.2] ..."). It is NOT necessarily the GitHub issue number. GitHub titles are the
  source of truth: before any `gh issue ...` call, resolve with `scripts/eng-issue.sh ENG-<n>`
  (prints the number; `scripts/eng-issue.sh <number>` prints the ENG id). Never write "#<n>" for
  an issue and never "ENG-#<n>". Pull requests are referenced as "PR #<n>".
- Branches: feat/ENG-<n>-<slug>, fix/ENG-<n>-<slug>, chore/ENG-<n>-<slug>, docs/ENG-<n>-<slug>,
  always created from origin/dev.
- PR titles: conventional commits ending in "(ENG-<n>)",
  e.g. "feat(api): validate Keycloak JWTs (ENG-3)". Commits add the task (see Commits).
- Every PR targets dev. Only release PRs (dev → main) and hotfix/\* target main.
- Don't use closing keywords ("Closes ..."); the close-issue workflow closes ENG-<n> on merge.
- Never push to dev or main directly. Never force-push.

## Planning

- Before starting an issue, read the current milestone plan and respect dependencies and lanes.
- Nothing from a later milestone than the current one. If an issue seems to need it, stop and
  tell me.
- Record design decisions as one dated line in the milestone's "Decisions" section; significant

## Rules

- Never modify an existing test to make it pass. If a test seems wrong, stop and ask me.
- No new dependencies (`go get`, `npm install <pkg>`, new Helm charts) without asking.
- Keep changes scoped to the issue.

### Test-Driven Development (mandatory)

Always follow TDD: write or identify the tests first, confirm they fail, then write the minimum code to make them pass, then refactor with the tests green.

- Before writing any implementation code, check whether tests already exist for the feature or module you are changing.
- If tests DO NOT exist: stop and propose a list of test cases covering both the happy path and the error paths (invalid input, edge cases, failures of dependencies). Wait for my approval before writing the tests or any implementation.
- If tests DO exist: use them as the specification. NEVER modify, delete, skip, or weaken existing tests to make code pass. If you believe an existing test is wrong or outdated, stop and explain why instead of changing it.
- Run the test suite after each change and report the results.

### Commits (mandatory)

- Create one commit per task within an issue. Never bundle multiple tasks into a single commit, and never make one commit for a whole issue.
- Commit as soon as a task is complete and its tests pass, before starting the next task.
- Reference the issue and task in the message, ONLY as ENG-<n> (never "#<n>" or "ENG-#<n>"),
  e.g. `feat(auth): add token validation (ENG-12, task 2/4)`.
- Do not squash, amend, or rewrite previous commits unless I ask.

## Gotchas

- Never edit an applied goose migration; create a new one.
- kubectl commands that change state must target the `kind-heimdall` context explicitly.
- RabbitMQ: ack only after the Job is created and the state is saved; on failure nack with
  requeue limits, never ack-then-process.
- SSE: Fiber needs a streaming body writer and the handler must stop when the client
  disconnects (watch ctx.Done()), or goroutines leak.
- ClickHouse prefers few large inserts: batch log lines, never insert line by line.
